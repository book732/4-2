# 보완 실험 및 최종 근거

환경: Ubuntu 26.04.1 LTS / WSL2 / x86-64, uid=1000, Python 3.14.4. 관측일 2026-11-20, 원본 시각 UTC+09:00 기준. 제공 x86-64 실행 파일은 수정하지 않았다.

각 쌍은 한 환경변수만 변경했고 관측 간격과 최대 관측 시간은 동일하게 설정했다. 실제 종료 시점은 자체 종료나 관측 제한에 따라 다르다. 제공 프로그램의 런처 대신 실제 작업 자식 PID를 관측했다.

## 보완 결과

- [메모리 보고서](../reports/01-oom.md): CPU 설정 30을 고정해 동일한 25MB 증가 패턴을 비교했다. 256MB는 보호 종료, 512MB는 525MB에서 캐시 복구 후 최소 90초 생존했다. 복구 직후 실제 RSS 18,292 KiB도 확보했다. 전체 내부 실행 경로가 같다고 단정하지 않는다.
- [CPU 보고서](../reports/02-cpu.md): 동일한 0.1초 관제로 짧은 피크를 수집했고 독립적인 연속 top도 추가했다. Before는 /proc 49.366%, top 50.0%와 명시적 Watchdog 메시지, After는 /proc 29.736%, top 30.0%와 60초 생존을 확인했다. 약 1초 평균과 순간 구간값의 차이도 설명했다.
- [데드락 보고서](../reports/03-deadlock.md): 기존 자원 획득·대기 로그, PID 유지, futex 대기, CPU/RSS 정체와 false 조건의 작업 진행 증거를 유지했다.

기존 기동 확인 1회와 초기 비교 5회에 보완 비교 4회를 추가했다. 위 표는 최종 근거 6회이며 CPU Before를 다른 케이스에서 재사용하지 않는다. 초기 탐색 증거는 evidence/에 그대로 보존했다. 새 보완 실행은 PTY로 터미널 출력을 수집해 급작스러운 종료 직전 메시지를 보존했다.

이 문서는 실제 관측과 추론의 범위를 구분한다. After의 수동 종료 코드는 앱 오류가 아니며, 60·90초 관측은 무기한 안정성의 증거가 아니다. Git 저장소 등록과 과제 제출은 별도 절차다.
